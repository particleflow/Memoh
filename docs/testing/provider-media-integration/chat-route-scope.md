# Catalog account-token scope regression

Base: `76f4ddad4f23699e01e13ede55c908b7fd87979c`. Pre-publication review identified
that the newly added media-catalog route inherited a credential-scope gap.

`auth.JWTMiddleware` intentionally skips account revalidation for signed
`typ=chat_route` tokens. `GenerateChatToken` defines these as route-reply
credentials; `UsersHandler.SendBotMessageSession` describes reply-only scope and
checks the token's Bot and saved route. The Server factory does not itself impose
a chat-token path allowlist, and the catalog handler originally did not reject
this token type. The presence of similar behavior in older provider routes does
not authorize a new external catalog request surface.

## Reproduction and narrow fix

`TestProviderMediaCatalogAccountScope` uses the actual
`server.NewServerWithSessionValidator` middleware/route stack, signed synthetic
JWTs, a query fixture and a real loopback HTTP catalog server. It invokes the
actual `ProvidersHandler` and provider service, never a real provider credential.
The query and account validator are test doubles; this is not a production
account revocation experiment or a new PG scope test.

The same assertions failed on the original product, then passed after adding a
guard only to `DiscoverMediaCatalog`. The guard uses the existing
`auth.ChatTokenFromContext` and existing `http.forbidden` error. It runs before
provider lookup and credential resolution and sends `Cache-Control: no-store`.
No global JWT behavior, old provider route group, role, team rule, destination,
credential path, official Agent core or other product API was modified.

| Credential | Before | After | After provider reads / upstream GETs |
| --- | --- | --- | --- |
| Active account | 200; account validator called once | 200; validator called once | 1 / 1 |
| Revoked account | 401 | 401 | 0 / 0 |
| Chat-route token identifying an active account | 200, validator bypassed | 403 | 0 / 0 |
| Chat-route token identifying a revoked account | 200, validator bypassed | 403 | 0 / 0 |
| Chat-route token with channel identity | 200, validator bypassed | 403 | 0 / 0 |
| Chat-route token in the supported query credential carrier | 200, validator bypassed | 403 | 0 / 0 |

Each of the four chat-token cases triggered exactly one upstream GET before the
fix. The [original failing output](scope-evidence/before.log) is retained, not
rewritten as a pass. The [race-enabled passing output](scope-evidence/after.log)
also covers the existing twelve catalog boundary cases, including anonymous,
revoked, foreign-team, redirect, malformed, disabled and empty-catalog behavior.
Exit codes were 1 before and 0 after.

The browser uses the [existing integration scripts](scripts/), not a new UI
implementation. Only the new scope cases assert chat-token rejection; do not
label the normal browser login as a chat-token test. Original logs are preserved
byte-for-byte, including tool whitespace. No token values, private Server logs,
configuration or raw DB rows are published.

The older provider management routes require a separately owned review/fix and
remain unchanged in this commit. This patch does not claim they are protected,
does not establish any production exposure, and does not declare the pending
combined candidate ready for publication. No images were published or deployed.
