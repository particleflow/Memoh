# Durable HTTP follow-up queue: isolated acceptance

Product: `efac3b837b6c5291c09a714dddb4b73251367361`; parent: `29685958ec896489371a894b6854ee8b2e9df9c5`. This is an independent increment after the c878 encoded invocation-path fix. It is not deployed or field-accepted. No paid provider, production database, account creation, UI change, or official Agent-core change was used.

## Confirmed defect and implementation

The default session runtime used MemoryBackend for both live coordination and follow-up items. A real HTTP202 item disappeared after process loss before admission: duplicate POST had returned the same item, but after restart the pending list was empty and its exact `follow-up:<item>` invocation was absent. The source run became lost under the existing reaper; no second B request was submitted to conceal the loss. See `evidence/red-result.json`.

The existing native-task queue is a different contract: `db/postgres/queries/native_task_queue.sql` attaches child task/tool records to the fenced source run's input. It does not represent an HTTP follow-up command, its requester, mutations, or a claim triggered after the source ends. Reusing those rows as unrelated HTTP tasks would fabricate task semantics. The fix instead implements the existing LiveQueueBackend interface in the application composition layer:

- `internal/followupqueue/store.go` and `backend.go` persist follow-up items, original invocation IDs, claim tokens, origin and promotion receipts in one PostgreSQL row per Bot/session. Transactions lock that row. Existing run coordination remains the MemoryBackend; the existing durable run ledger and application admission remain the execution authority. Redis composition is unchanged.
- `internal/handlers/session_queue.go` marks authenticated HTTP origin in context. Duplicate invocation replay returns the original item before requiring another active source run; changed payload conflicts. Existing queue limits are reused. No new business time, ID, name, workspace or attempt-count condition is introduced.
- `cmd/internal/core/durable_followup.go` checks the original account, current Bot/session permission and original fixed contact before HTTP claim. Permission queries run outside the queue transaction, then claim checks that the same payload/origin still holds under the row lock. A one-connection PostgreSQL pool is covered; correctness does not require a spare permission-query connection.
- Startup reconciles claims against the original `follow-up:<item>` ledger identity. An admitted run remains that run, including failed/lost states. An unproved claimed admission becomes visible unknown and is not replayed. A terminal source with an unclaimed HTTP item is woken through the existing application admission path. An active source continues through the existing terminal observer/reaper. No extra scheduler/service or retry loop is introduced.
- Promotion persists intent before interacting with transient steer state. Unproved promotion after process loss is retained as unknown; it is not reinjected. The claim token is a queue receipt, not proof of model execution: concurrent callbacks may observe the same claim, while original-invocation admission supplies execution deduplication.
- Queue history and unknown receipts have no TTL or destructive compaction. The new table has no cascading deletion. Credential-bearing payloads use the existing `auth.agent_credentials_encryption_key` capability, AES-GCM with Bot/session-associated data. No credential is generated. Credential-free payloads can be stored without that key; credential-bearing writes without it fail before persistence. Missing/wrong decrypt capability returns an error, never an empty queue. JWT rotation is not used as an encryption mechanism.

## Migration, upgrade and recovery contract

Candidate migration `0182_session_follow_up_queue` adds one table; the canonical init snapshot and SQLC source/generated models are updated. Integration must confirm the migration number is still available on its actual head. In isolation, forward migration181 clean →182 clean succeeded. The exact182 down SQL is a preservation no-op; the exact182 up is additive/idempotent. Applying those two specific SQL files inside a controlled transaction preserved all stored envelope hashes. This is **not** validation of the repository's global CLI down operation.

Upgrade must account for the old binary's already-accepted memory items. Let those items naturally finish while the old writer remains alive; do not kill them, pause schedules, manufacture receipts, or infer commands from a list GET. The public queue projection does not contain enough authority/command data to reconstruct lost old-memory items. A crash before this patch cannot be repaired by inventing an item. Check the actual configured runtime backend and existing encryption capability before replacing the writer. Apply the additive migration with the supported forward process, retain the original key and historical records, then start the new writer. Existing permission and workspace resolution still apply.

Rollback is not a destructive database down. Preserve the new table, envelope bytes, key and run/history records. An older memory-only binary cannot consume pending durable items; use a reader-compatible rollback build, or establish that all safely executable pending work has naturally drained before returning to that binary. Unknown items are retained for explicit supported recovery, not consumed to make a drain check pass. Key rotation requires retaining access to old ciphertext or a deliberate compatible re-encryption migration; deleting/replacing the key is not a supported queue recovery. This increment does not add key rotation or an administrative unknown-replay endpoint.

Startup errors are reported per queue and preserve its contents. The app does not silently declare a broken queue empty. The explicit startup wake covers HTTP-origin pending work; non-HTTP result items continue to use the existing result/terminal mechanisms. Redis changes, cross-instance orchestration, high-volume retained-row performance, key-rotation migration, and every possible promotion crash boundary are not claimed as accepted here.

## Isolated migration incident: preserved, not hidden

During compatibility work, the owner mistakenly ran `memoh-server migrate down` expecting one step. The command calls the migration library's `Down()` and attempts **all** downs. On the disposable clone `memoh_queue_post_identity_20261030`, it went from182 down through43 and failed at42, leaving42 dirty. Later experimental session-run and delegation tables were removed; messages/new queue envelopes remained. Production and the original source database were never targets. No business fixture was active at that time.

The damaged clone was quarantined without force/version rewriting. Its remaining contents were dumped privately. A separate database `memoh_queue_durability_recovered_20261030` was restored from the existing pre-queue-test snapshot and migrated forward. Later experimental run/delegation metadata removed by the erroneous down was **not reconstructed**. The final busy and exact-efac terminal tests above ran on this restored database. `evidence/fixture-recovery.json` records both dump hashes and the restore boundary. Dumps contain private data and are not checked in. No global CLI down was repeated. The old fixture config must not be used against the quarantined database.
