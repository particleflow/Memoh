## Upload wiring and recovery matrix

The retained `NativeResumableUpload.ets` is now called by the existing native
router and shared composer. The file/photo menu uses its picker. Clipboard,
drop and completed recording Files use `File.slice` chunks of at most 64 KiB to
copy into the same native snapshot, then call the same uploader. They do not use
whole-file `File.arrayBuffer`, Web multipart or a new NAS API for this path.
The existing microphone capture/finish-to-File lifecycle is unchanged; this is
not recovery of an unfinished recording. Picker originals never cross the Web
bridge. Native network chunks remain capped at 256 KiB.

All network uploads retain the Bot-scoped `/bots/{bot}/media/uploads` contract,
same NAS Media/originals storage and account/Bot/session ownership. No PC task
lease, new root, global backlog quota or receipt-expiry extension was introduced.
The existing 24-hour generic receipt expiry is not a durability guarantee.

| Event | Implemented behavior | Current evidence |
| --- | --- | --- |
| Create before send / lost reply / process kill | Atomically persist `create-unknown` first; never automatically POST again without a known ID. Existing API cannot resolve a missing ID, so preserve the original and report uncertainty. | Four independent-process Create cases; Create 429 is also not re-POSTed |
| GET original receipt returns 404 | Keep original ID, offset, expiry and source; no reset, multipart fallback or new Create. | Original and expired receipt cases |
| PATCH reply lost | GET the same ID, then continue from its authoritative offset. | Lost reply, 409 and process restart cases |
| Complete reply lost | Persist `completePending` first; GET only that ID. If still uploading, report uncertainty rather than repeat Complete. | Complete-unknown and Complete-lost cases |
| Ready | Require exact hash/size/offset from NAS and unchanged local snapshot. Reopened ready originals require an authenticated HEAD with matching hash/size; 404 cannot yield a stale reference. | Corruption, ready HEAD404, repeated-ready cases |
| Pause / tab lifecycle / account close | Stop I/O and revoke preview handles, retain committed local snapshots. Reopen previews only after account/Bot/scope reauthorization. | Pause, exact-handle reauthorization and router cases |
| Chat confirmed | Remove only the local snapshot/journal. Never DELETE a committed NAS original. Failed or ambiguous send retains the original. | Actual generated chat store and consume cases |

The existing restore control recovers a bounded window of 16 snapshots; explicit
draft restore preserves the old draft scope. This is not a new total quota.
Only one of the 43 existing adaptation targets, `chat-pane.vue`, changed; the
other 42 patch hashes remain equal to source checkpoint `b1a025dc`.

`upload-current-matrix.json` records 39 current cases using production `.ets`

`native-router-preview.json` checks the actual native command router and scoped

## Download recovery

The actual native download class now stores a private fsync/rename checkpoint
under the existing application's files directory. The key binds the configured
API authority, authenticated user, Bot, exact ordinary/delegation path, content
hash and size. The journal contains only that digest, hash, size and byte offset;
credentials, endpoint, names and message text are not persisted in this journal.
A new foreground attempt can reopen the same checkpoint with a new operation
handle after restarting. A fresh `/users/me` and the original scoped GET/HEAD
recheck access. Authorization failure never falls back to the Bot/hash route.
Uncommitted file tails are truncated to the durable offset. Full SHA-256 and size
verification precede the existing system picker/save path.

Explicit cancel discards the active app-owned download. Page/account lifecycle
release cancels I/O while retaining its checkpoint for a later authorized retry.
There is no background credential, new scheduler, endpoint or transfer service.
The phone still uses the configured NAS origin and platform routing; this does
not claim that the PC's explicit LAN dial policy was implemented on Harmony.

`download-byte-check.json` runs the production `.ets` class through Node adapters
for Harmony FS/crypto/RCP/picker boundaries, with real disk files and local HTTP.
It transfers 18 MiB, exercises a literal SIGKILL after a durable 262,144-byte
checkpoint, then starts another process. Its first GET resumes at that offset;
the final saved SHA-256 is equal. The test also covers stale uncommitted tails,
account isolation, delegated-cache HEAD authorization, invalid ranges/ETags,
corrupt bytes, network cancellation, short writes, disk failure and copy errors.
Read/write buffers are capped at 256 KiB; this is not a phone memory benchmark.

`download-bridge-check.json` executes the actual Web bridge and native command
router with controlled SDK/OS seams. It verifies no response body enters the
WebView, explicit cancellation, lifecycle release, stale login protection and
unchanged frame/ready gates. It is not native OS execution.
