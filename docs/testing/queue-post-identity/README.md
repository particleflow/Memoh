Product patch: `c878a31e268119939330d9eed52050539636b306`, based on `f74e462b20f49b6167c90baf9a7a2bd1b51bdcfc`. Only the HTTP invocation lookup and its router regression test change. No Agent core, queue, scheduling, UI, authorization or schema change. This is cloud isolation evidence, **not a production queue acceptance**.

## Defect and correction

The real handler accepted two concurrent identical follow-up POSTs with HTTP202 and the same item ID. The admitted invocation is `follow-up:<item_id>` (`internal/agent/application/queue_continuation.go`, `followUpCommand`). A client correctly escaping that opaque path segment produced `%3A`, but the invocation handler queried the literal escaped string and returned HTTP200/found=false although the original run had completed in PostgreSQL.

`red-path-proof.json` holds both responses for the same original item. `router-red.txt` independently reproduces the problem through Echo's actual router, not manually injected parameters. Echo `GetPath` uses URL.RawPath if present and URL.Path otherwise. The patch decodes only the RawPath case, exactly once. It is not a follow-up prefix, Bot ID, native runtime or test-name exception. Tests include encoded and literal colon, literal percent sequences, mixed escapes, plus and slash. The session authorization and scoped ledger lookup stay in place.

`router-green.txt`: all seven existing invocation endpoint tests plus the new six-case router test passed, including cross-session and denied-access boundaries. No unrelated suites were rerun. Build: Go1.25.7, `go build -buildvcs=false -o /tmp/queue-post-identity/memoh-server-fixed ./cmd/agent`; exact source and binary digest are recorded in `manifest.json` because this worktree's VCS stamping is unavailable.

## Persistence boundary still open

Do not describe this test as a durable pending HTTP queue test. `SessionRuntimeConfig.BackendOrDefault` selects memory when unspecified; `session/config.go` installs `MemoryBackend`, and `memory_live_queue.go` stores pending follow-ups in a process-local map with state TTL. PostgreSQL durably records the admitted run and history. The original native task admission queue and schedule fire persistence are separate mechanisms and do not prove this HTTP pending queue survives server loss.

Redis is an existing alternative (`redis_live_queue.go:EnqueueFollowUp`, JSON state with configured TTL), but no Redis backend was configured/running in this isolated environment; its persistence/failover guarantees were not exercised. No new service was created to claim that coverage. Client reconnect PASS is **not** a server-crash-before-admission PASS. Parent should keep pending follow-up crash recovery as an explicit remaining source/acceptance gap; do not silently switch production backend, replay an unknown item or claim the native queue tests cover it. Any fix must respect the original no-Agent-core constraint and use existing application/persistence contracts; this patch does not attempt that separate change.
